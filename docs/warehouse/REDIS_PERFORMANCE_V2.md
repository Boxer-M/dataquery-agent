# Redis Performance Benchmark v2

两类负载均通过真实 Uvicorn HTTP 聊天入口、当前 Capability、正式 SQL 模板与本机 PostgreSQL。固定意图回调供各组复用。Catalog 的这两项正式指标使用 SQL Shed 数据仓。

| 负载 | 正式口径与业务路径 |
| --- | --- |
| 简单查询 | 120 个自然日的订单量。单次查询聚合 `dws.order_day`。 |
| 关联聚合 | 120 个滚动 180 日窗口的折扣后商品销售金额，按月及品类分组。现有模板关联 `dws.product_sales_day` 与 `dim.product`，按时间桶执行。 |

各负载以并发 1、5、8 测试 Redis 关闭、冷缓存和热缓存。每档三轮，每轮 120 个请求。测量阶段交换模式顺序。冷组每轮换缓存版本，热组先填满同一组键。各组成功响应逐题核对数据、行数及截断标记。脚本开始和结束用同一只读证明核对启用的来源字段及 Catalog，同一负载间隔 65 秒。每个模式和负载共 1080 个正式请求。单独的限流压力组使用 24 个请求。

## 耗时口径

| 阶段 | 计时边界 |
| --- | --- |
| API 初始化 | 进入处理器到 Owner 与 Manager 就绪，包含本次请求的 Capability 元数据快照。 |
| 路由与执行 | 会话 claim、意图路由、工具执行及历史完成，包含下列部分子阶段。 |
| Capability | 调用现有 Capability Resolver。 |
| Redis | 读写、填充锁和适用时的 Lua 限流命令往返。 |
| ACL | 命中时建立 PostgreSQL 指标角色连接并完成权限探测。 |
| 指标 SQL | 正式模板 `pg.execute` 调用。另记录完整 SQL 工具耗时，含连接、参数设置和结果转换。 |
| 响应组装 | API 公共响应投影及 JSON 序列化。 |
| HTTP | 客户端发送至收完整响应。 |

应用阶段百分位使用成功响应中实际经过该阶段的样本。指标 SQL 总耗时累加实际调用，HTTP 延迟使用测量批次全部请求。阶段包含关系和百分位的样本排序使各阶段 P95 无法直接相加。

## 复现

~~~sh
.venv/bin/python -m pip install -r requirements-redis.txt
docker compose -f compose.redis.yaml up -d redis
PYTHONPATH=src .venv/bin/python scripts/benchmark_redis.py --v2 --workload simple \
  --round-pause 65 --out /tmp/redis-v2-simple.json
PYTHONPATH=src .venv/bin/python scripts/benchmark_redis.py --v2 --workload aggregate \
  --round-pause 65 --out /tmp/redis-v2-aggregate.json
PYTHONPATH=src .venv/bin/python scripts/benchmark_redis.py --levels 5 \
  --out /tmp/redis-v2-v1-replay.json
~~~

前两次长跑在不同并发上限下均遇到 Docker 发布端口上的 PostgreSQL 连接断开，容器保持运行。重测采用并发上限 8，三轮之间冷却 65 秒，两个负载分别执行。冷却和预热不纳入 QPS。客户端传输失败保留计数，单批超过 5% 时脚本结束测量。

## 决策

- **v1 的 P95**。复测 v1 同一批月度查询后，关闭和热缓存的 P95 分别为 113.12 和 123.12 ms。关闭时指标 SQL 的 P50 为 2.26 ms，完整 SQL 工具为 11.22 ms。热命中的 ACL 探测为 9.24 ms，Redis 为 0.65 ms。每请求初始化仍需加载元数据，P50 约 59–65 ms。阶段数据支持 v1 的判断，缓存能消除简单指标 SQL，端到端尾延迟仍受请求初始化与权限探测影响。
- **值得缓存的查询**。高重复率的长窗口、多表关联及分组趋势查询收益更明显。并发 5 的 360 次关联聚合中，热缓存把 2481 次指标 SQL 和累计 5684.44 ms 的调用时间降为零，保留 360 次 ACL 探测。P95 下降 15.9%，完成吞吐提升 20.8%。
- **负载与容量**。并发 8 下，关联聚合完成吞吐从 44.85 增到 50.72 QPS，P95 从 203.42 降到 180.88 ms。简单查询的完成 QPS 接近关闭组。指标 SQL 和 ACL 之外还有元数据、会话和历史事务，本次服务容量结论适用于本机及已测阶梯。
- **缓存粒度与 TTL**。优先使用当前完整结构化请求键和 60 秒 TTL。数据发布继续切换数据版本。重复查询收益已经可见，TTL 和粒度调整需要真实流量的重复周期与新鲜度目标。
- **ACL 优化**。简单查询的 ACL 探测成本接近完整 SQL 工具。进一步优化值得测连接建立耗时及连接复用，并保留当前 Owner、Capability 和实际权限检查。初始化同样值得单独剖析。

简历可引用「在真实 HTTP、Redis、PostgreSQL 的三轮 360 请求对照中，带实时权限校验的热缓存将跨月品类聚合的指标 SQL 从 2481 次降至 0 次，每次命中复核 ACL。并发 5 时 P95 下降 15.9%，完成吞吐提升 20.8%。」

## 安全回归

Python 全量执行 229 项，227 通过，两项可选外部模型测试跳过。真实 Redis 与 PostgreSQL 专项覆盖 Owner 隔离、Catalog 与数据版本失效、同键单次填充、连接拒绝后的 SQL 回退及阶段计时。热命中撤权分支使用故障注入，实际 PostgreSQL 角色另行验证对无权来源的拒绝。Redis 开启下的 HITL 与 Catalog 定向恢复专项三项通过。

  .venv/bin/python -m unittest -v test_redis_performance

  DATAQUERY_RATE_LIMIT=0 HITL_POSTGRES_TESTS=1 KNOWLEDGE_POSTGRES_TESTS=1 PYTHONPATH=src:tests \
  .venv/bin/python -m unittest -v test_hitl test_catalog_recovery
~~~
